## 1. Що робить цей модуль

Audit Log веде історію операцій над обраними вами моделями Odoo. Ви створюєте одне **правило** на модель (наприклад, *Contact* — Контакт), обираєте, які операції відстежувати, і підтверджуєте правило. Відтоді кожна відстежувана операція створює **журнал** (хто, коли, який запис, яка операція) з одним **рядком журналу** на кожне змінене поле, де показано старе і нове значення. Аудитори, адміністратори та фахівці з комплаєнсу використовують модуль, щоб відповісти на питання «хто це змінив і що було раніше?».

| Можливість | Деталі |
|---|---|
| Правила аудиту для моделей | Одне правило на модель (`auditlog.rule`); друге правило для тієї ж моделі відхиляється з повідомленням «There is already a rule defined on this model.» |
| Відстежувані операції | Створення, зміна, видалення, читання та експорт — кожну можна вмикати окремо |
| Історія на рівні полів | Кожен рядок журналу зберігає назву поля, технічне ім'я, «сире» та зручне для читання старе/нове значення |
| Зрозумілі значення зв'язків | Значення Many2one та many2many/one2many показуються як назви записів; запис, якого вже не існує, показується як `<id> (DELETED)` |
| Знімок видаленого запису | З опцією **Capture Record** журнал видалення зберігає всі значення полів запису безпосередньо перед видаленням |
| Відстеження експорту | Один журнал на експорт зі списком ідентифікаторів експортованих записів і розумною кнопкою **Exported Records**, яка знову їх відкриває |
| Винятки | Для кожного правила — користувачі-винятки (наприклад, інтеграційні) та поля-винятки (наприклад, нотатки) |
| Слід сесій і запитів | Кожен журнал пов'язаний із сесією користувача та HTTP-запитом (шлях URL), що його спричинили |
| Ізоляція між компаніями | Журнал отримує компанію запису, що перевіряється; користувачі бачать лише журнали дозволених їм компаній |
| Зберігання | Необов'язкова запланована дія видаляє дані аудиту, старші за 180 днів |
| Ярлик «View logs» | Підтвердження правила додає дію **View logs** (Переглянути журнали) на форму моделі, що перевіряється (меню «Дії») |

## 2. Де знайти модуль в Odoo

Модуль розташований у технічних налаштуваннях, тому **має бути ввімкнено режим розробника** (Settings → Activate the developer mode). Батьківське меню **Audit** бачать лише адміністратори налаштувань (`base.group_system`).

**Шлях:** `Settings` → `Technical` → `Audit` (Налаштування → Технічні → Аудит)

| Меню | Призначення | Хто бачить |
|---|---|---|
| **Rules** (Правила) | Створення, підтвердження та повернення правил аудиту в чернетку | Auditlog User (читання), Auditlog Manager (редагування) |
| **Logs** (Журнали) | Один рядок на кожну операцію; відкрийте, щоб побачити зміни полів | Auditlog User і вище |
| **Log Lines** (Рядки журналу) | Плаский список усіх змін полів з усіх журналів, пошук за старим/новим значенням | Лише **Access Rights** (`base.group_erp_manager`) |
| **User sessions** (Сесії користувачів) | Сесії входу, що створили журнали, з їхніми HTTP-запитами | Auditlog User і вище |
| **HTTP Requests** (HTTP-запити) | Окремі запити (шлях URL + кореневий URL) і журнали, які вони створили | Auditlog User і вище |
| **Delete Old Logs** (Видалити старі логи) | Вікно, яке одразу видаляє старі дані аудиту (див. розділ 7, Зберігання) | Auditlog Manager |

Крім того, на формі будь-якої моделі під аудитом (наприклад, контакту) пункт **Actions (шестерня) → View logs** показує журнали саме цього запису.

На формі правила розумна кнопка **Logs** (Логи; праворуч угорі, напр. **29 Логи**) відкриває всі журнали моделі цього правила.

## 3. Початкове налаштування: створення правила аудиту

> ⚠️ Нічого не записується, доки хоча б одне правило не буде в стані **Confirmed** (Підтверджено).

**Шлях:** `Settings` → `Technical` → `Audit` → `Rules` → `New`

| Поле | Що вводити | Приклад |
|---|---|---|
| **Name** (Назва) | Довільна назва правила | `Partner audit trail` |
| **Model** (Модель) | Модель для аудиту. Тимчасові (transient) моделі та самі моделі `auditlog.*` обрати не можна | `Contact` (`res.partner`) |
| **Type** (Тип) | **Full log** (Повний журнал, за замовчуванням) або **Fast log** (Швидкий журнал) — див. [розділ 6](#6-повний-журнал-і-швидкий-журнал) | Full log |
| **On Logging Failure** (У разі збою журналювання) | **Block the operation** (Заблокувати операцію, за замовчуванням) або **Skip the log** (Пропустити запис журналу) — див. [розділ 7](#7-політика-збоїв-кілька-компаній-і-зберігання) | Block the operation |
| **Log Creates** | Відстежувати створення записів (за замовчуванням увімкнено) | ✅ |
| **Log Writes** | Відстежувати зміни (за замовчуванням увімкнено) | ✅ |
| **Log Deletes** | Відстежувати видалення (за замовчуванням увімкнено) | ✅ |
| **Log Reads** | Відстежувати кожне читання/відкриття запису (за замовчуванням вимкнено — ресурсоємно) | ❌ |
| **Log Exports** | Відстежувати експорт (за замовчуванням увімкнено) | ✅ |
| **Capture Record** | Під час видалення зберігати повний знімок значень видаленого запису | ✅ |
| **Users to Exclude** (вкладка, Користувачі-винятки) | Користувачі, чиї операції ніколи не записуються | `OdooBot`, користувач API-інтеграції |
| **Fields to Exclude** (вкладка, Поля-винятки) | Поля обраної моделі, для яких ніколи не створюється рядок журналу | `Notes` (`comment`) |

Потім натисніть **Confirm** (Підтвердити). Рядок статусу переходить з **Draft** (Чернетка) у **Confirmed**, створена дія «View logs» прив'язується до форми моделі (її технічний запис поле **Action** показує лише в режимі розробника), і аудит починається негайно. Кнопка **Logs** веде до журналів правила.

**Зміна статусів:** Draft → Confirmed (→ Set to Draft → Draft)

> 💡 Коли правило підтверджено, усі його поля конфігурації стають лише для читання. Щоб змінити операції, тип або винятки, натисніть **Set to Draft** (Повернути в чернетку), відредагуйте і знову натисніть **Confirm**. Поки правило в чернетці, для цієї моделі нічого не записується, а дія «View logs» зникає з форми моделі; повторне підтвердження використовує ту саму дію.

## 4. Перегляд журналів

**Шлях:** `Settings` → `Technical` → `Audit` → `Logs`

Список показує **Date** (Дата), **Resource Name** (Назва ресурсу), **Model** (Модель), **Method** (Метод: `create`, `write`, `unlink`, `read`, `export_data`) і **User** (Користувач). Необов'язкові колонки: Resource ID, Type і (для користувачів з кількома компаніями) Company.

Фільтри: **Create**, **Write**, **Delete**, **Read**, **Export**. Групування: **User**, **Model**, **Method**, **Company**, **Date**.

Відкритий журнал містить:

| Область | Вміст |
|---|---|
| Група **Log** | Дата, користувач, метод, тип, компанія (лише в режимі кількох компаній) |
| Група **Resource** | Назва ресурсу, модель, технічна назва моделі, ID ресурсу, Resource IDs (лише для експорту) |
| Вкладка **Fields updated** (Оновлені поля) | Один рядок на поле: Description (Опис), Old value Text (Старе значення), New value Text (Нове значення); «сирі» значення та технічне ім'я доступні як необов'язкові колонки |
| Вкладка **Technical** (Технічне) | Сесія та HTTP-запит, що створили журнал |
| Розумна кнопка **Exported Records** | Лише в журналах експорту: відкриває експортовані записи (зрозуміле повідомлення про помилку, якщо модель видалено) |

Журнали, сесії та запити в інтерфейсі доступні лише для читання (немає кнопок створення/редагування).

**Log Lines** (`Settings` → `Technical` → `Audit` → `Log Lines`) — плаский перегляд усіх змін полів лише для читання, зручний для питань на кшталт «хто взагалі встановлював цю email-адресу?». Шукайте за **Old value Text** / **New value Text**, фільтруйте за Create/Write/Delete і групуйте за User, Model, **Field** (Поле) або Company.

## 5. Основні сценарії

### Сценарій 1: Дізнатися, хто перейменував клієнта (приклад)

Налаштування: правило *Partner audit trail* для `Contact`, Full log, увімкнено Log Writes, стан Confirmed.

1. Менеджер з продажу відкриває контакт **Azure Interior**, змінює **Name** на `Azure Interior SA` і зберігає.
2. Створюється рівно **один** журнал `write`:

   | Поле журналу | Значення |
   |---|---|
   | Resource Name | Azure Interior SA |
   | Model | Contact |
   | Method | write |
   | User | менеджер з продажу |
   | Type | Full log |

3. Вкладка **Fields updated** містить по одному рядку на кожне змінене поле — тут це поле, яке редагував користувач:

   | Description | Old value Text | New value Text |
   |---|---|---|
   | Name | Azure Interior | Azure Interior SA |

   Оскільки повний журнал порівнює всі збережені поля, збережене обчислюване поле, що змінюється як наслідок (у контактів зазвичай **Complete Name** — Повна назва), отримує власний рядок з тими самими старим/новим текстами. Більше нічого не показується.

4. Аудитор знаходить журнал або через **Logs** → фільтр **Write** → пошук `Azure`, або прямо з форми контакту: **Actions → View logs**.

Поля, значення яких не змінилося, не створюють рядків; `create_date`, `write_date`, `create_uid`, `write_uid` і `display_name` ніколи не записуються.

### Сценарій 2: Розслідувати видалення запису

Якщо ввімкнено **Log Deletes** і **Capture Record**, видалення контакту створює журнал `unlink`, у вкладці **Fields updated** якого перелічено всі збережені поля з їхнім останнім значенням в **Old value Text**. Без Capture Record журнал `unlink` все одно фіксує, хто видалив запис з яким ID, але без рядків.

### Сценарій 3: Перевірити, що було експортовано

З увімкненим **Log Exports** кожен експорт (список → виділити → Actions → Export) створює один журнал `export_data`. Поле **Resource IDs** містить JSON-список експортованих ID; розумна кнопка **Exported Records** (наприклад, «12 Exported Records») знову відкриває саме ці записи. Внутрішнє читання під час експорту окремо не записується, тож експорт не засмічує журнал записами читання.

### Сценарій 4: Виключити «шумного» користувача або поле

Поверніть правило в чернетку, додайте користувача в **Users to Exclude** або поле в **Fields to Exclude** і натисніть Confirm. Починаючи з наступної операції, дії виключеного користувача не записуються взагалі, а для виключеного поля ніколи не створюється рядок (інші змінені поля в тому самому збереженні записуються).

## 6. Повний журнал і швидкий журнал

| | **Full log** (Повний, за замовчуванням) | **Fast log** (Швидкий) |
|---|---|---|
| Що читається | Усі збережені не-бінарні поля запису **до і після** операції | Нічого додатково — лише значення, передані в create/write |
| Старі значення при зміні | Справжні попередні значення | Завжди показуються як `False` |
| Побічні зміни (збережені обчислювані поля) | Записуються | Не записуються |
| Вартість | Два додаткові читання на кожну зміну | Мінімальна |
| Найкраще для | Комплаєнсу, моделей з невеликим/середнім обсягом | Моделей з великим обсягом, де достатньо знати «що було надіслано» |

**Приклад — те саме перейменування з Fast log:** рядок показує **Old value Text** `False`, **New value Text** `Azure Interior SA`. Ви знаєте, що записали, але не знаєте, що було замінено.

Спільне для обох типів:
- Під час **створення** поля з порожніми початковими значеннями (порожній текст, `False`, порожні списки) пропускаються, тож новий контакт лише з Name та Email дає два рядки, а не сорок.
- Бінарні поля (зображення, вкладення) ніколи не записуються.
- Значення зв'язків показуються назвами, наприклад Tags `VIP, Wholesale`; тег, якого вже не існує, показується як `7 (DELETED)`.

## 7. Політика збоїв, кілька компаній і зберігання

### On Logging Failure (У разі збою журналювання)

| Налаштування | Якщо запис аудиту не вдалося зберегти… | Коли використовувати |
|---|---|---|
| **Block the operation** (за замовчуванням) | Операцію користувача скасовано (відкат), користувач бачить помилку. Жодної зміни без сліду. | Комплаєнс вимагає гарантованого сліду |
| **Skip the log** | Операція користувача виконується; помилку записано в журнал сервера; **запису аудиту** для цієї операції немає | Безперервність бізнесу важливіша за повноту |

### Конфігурація «наживо»

Тип правила, винятки, Capture Record і політика збоїв зчитуються з бази даних під час **кожної** операції, що журналюється, тож зміна діє негайно в усіх робочих процесах сервера — перезапуск не потрібен.

### Кілька компаній

- Кожен журнал зберігає **компанію запису, що перевіряється** (якщо модель має поле `company_id`); експорт отримує компанію лише тоді, коли всі експортовані записи належать одній компанії.
- Журнали, рядки журналу, перегляд Log Lines, сесії користувачів і HTTP-запити видно лише тоді, коли їхня компанія входить до **дозволених компаній** користувача, або якщо компанії немає (наприклад, журнали моделей без поля компанії).
- Самі правила глобальні: одне правило для `Contact` перевіряє контакти всіх компаній.
- Колонка/фільтр/групування **Company** приховані для користувачів з однією компанією і з'являються в режимі кількох компаній.

**Приклад:** змінено контакт компанії *Auditlog Demo Company B*. Користувач, якому дозволено лише головну компанію, не бачить цього журналу в **Logs** чи **Log Lines**; користувач з доступом до обох компаній — бачить.

### Зберігання (автоочищення)

**Шлях:** `Settings` → `Technical` → `Automation` → `Scheduled Actions` → **Auto-vacuum audit logs**

| Властивість | Значення |
|---|---|
| Стан після встановлення | **Неактивна** — нічого не видаляється, доки ви її не ввімкнете |
| Частота | Щодня |
| Код | `model.autovacuum(180)` — зберігає 180 днів |
| Що видаляється | Журнали (з рядками), HTTP-запити та сесії користувачів, старші за період зберігання, починаючи з найстаріших |

Щоб зберігати рік, змініть код на `model.autovacuum(365)` і позначте **Active**. Запускати очищення можуть лише Auditlog Manager.

**Запуск вручну:** `Settings` → `Technical` → `Audit` → **Delete Old Logs** (Видалити старі логи) відкриває вікно з полями **Keep Last (Days)** (Зберігати останні (днів), типово `180`) і **Chunk Size** (Розмір пакета, `0` = без обмеження; інакше максимальна кількість записів, що видаляються для кожної моделі за цей запуск). Натисніть **Delete Old Logs**: сповіщення підтверджує «Дані аудиту, старші за 180 днів, видалено.» Приклад: зі значенням `90` 25.09.2026 видаляються всі журнали, створені до 27.06.2026 включно (разом із рядками), а журнали з липня залишаються.

### Сесії та запити

- **User sessions**: **Session ID** — це відбиток SHA-256 ідентифікатора HTTP-сесії, а не сам ідентифікатор, тому його не можна використати для перехоплення сесії. Відображувана назва: `<користувач> (<дата>)`.
- **HTTP Requests**: зберігає **Path** (Шлях, наприклад `/web/dataset/call_kw/res.partner/web_save`), **Root URL**, користувача, сесію та пов'язані журнали. Контекст користувача не зберігається.
- Операції поза HTTP-запитом (заплановані дії, скрипти в оболонці) створюють журнали без сесії/запиту.

## 9. Ролі доступу

| Роль | Правила | Журнали / рядки / сесії / запити | Меню Log Lines | Автоочищення |
|---|---|---|---|---|
| **Auditlog User** | ✅ Читання | ✅ Читання (дозволені компанії) | ❌ (якщо немає Access Rights) | ❌ |
| **Auditlog Manager** (включає User) | ✅ Читання, створення, редагування, видалення, Confirm / Set to Draft | ✅ Повний доступ (дозволені компанії) | ❌ (якщо немає Access Rights) | ✅ |
| **Access Rights** (`base.group_erp_manager`) | — | — | ✅ Читання | — |
| **Settings** (`base.group_system`) | Автоматично Auditlog Manager | Автоматично Auditlog Manager | ✅ (Settings включає Access Rights) | ✅ |

Під час встановлення користувач admin стає Auditlog Manager. Оскільки меню **Audit** розташоване в **Settings → Technical**, щоб дістатися до нього через меню, потрібні роль Settings і режим розробника.

Як призначити: `Settings` → `Users & Companies` → `Users` → оберіть користувача → поле **Auditlog Rights** на вкладці Access Rights.

## 10. Обмеження

| Тема | Обмеження |
|---|---|
| Спосіб реалізації | Модуль підміняє методи ORM (`create`, `write`, `unlink`, `read`, `export_data`) класів моделей під аудитом на рівні реєстру — той самий прийом, що й у `base_automation` Odoo. У межах одного релізу це надійно, але закладайте перегляд/переписування під час кожного мажорного оновлення Odoo. |
| Журналювання читання | **Log Reads** створює один журнал на кожен прочитаний запис під час кожного читання, включно зі списками та автоматичними читаннями. На навантажених моделях (контакти, товари) це швидко збільшує базу і сповільнює інтерфейс. Вмикайте лише для чутливих моделей з невеликим обсягом. |
| Fast log | Не показує старі значення (завжди `False`) і не фіксує побічні зміни. |
| Перегляд Log Lines | SQL-представлення лише для читання; його не можна редагувати чи видаляти з нього — очищається лише через відповідні журнали. |
| Транзакції лише для читання | Журнали, створені під час запитів лише для читання (наприклад, журналювання читання), записуються через окремий курсор бази даних, тож вони зберігаються, навіть якщо сам запит потім завершиться помилкою. |
| Прямий SQL | Зміни, зроблені «сирим» SQL або кодом в обхід методів ORM, не записуються. |
| Бінарні поля | Зображення та файли ніколи не записуються. |
| Область дії правила | Одне правило на модель; правило не можна обмежити компанією чи доменом записів; моделі `auditlog.*` і тимчасові моделі перевіряти не можна. |
| Редагування підтвердженого правила | У стані Confirmed конфігурація лише для читання; використовуйте Set to Draft → редагування → Confirm (поки правило в чернетці, нічого не записується). |
| Захист від підробки | Auditlog Manager (а отже й адміністратори Settings) можуть видаляти журнали. Модуль — це слід аудиту, а не криптографічно захищений реєстр. |
| Зберігання | Автоочищення постачається неактивним; якщо його не ввімкнути, журнали зростають безмежно. |
| Інтеграції | Немає експорту в SIEM чи зовнішні системи журналювання; немає звітів (PDF). |
