# Вид товару — Виробнича класифікація — Посібник користувача

## 1. Огляд

**Вид товару** (`odomate.product.kind`) — це ієрархічна виробнича класифікація
ваших товарів. На відміну від стандартної категорії товару, Вид товару несе
виробничу семантику (тип маршруту, режим виробництва, прапорці інженерії та
планування бригад) і — найголовніше — **фіксує знімок** на рядках замовлень на
продаж та на виробничих замовленнях у момент їх підтвердження чи створення.

Результат: товар можна перекласифікувати будь-коли, і зміна миттєво поширюється
на товар та його специфікацію (*жива прив'язка*), тоді як кожен уже підтверджений
документ продажу та виробництва зберігає той вид, який мав на момент
підтвердження (*зафіксований знімок*).

## 2. Встановлення

1. Скопіюйте теку `odomate_product_kind` у ваш шлях додатків Odoo.
2. Модуль залежить від **Виробництва** (`mrp`), **Продажів** (`sale`) та
   **Ієрархічного вигляду** (`web_hierarchy`) — Odoo встановить їх автоматично.
3. Оновіть список додатків і встановіть **Вид товару — Виробнича класифікація**.

## 3. Безпека та ролі

| Група | Технічна назва | Права |
|-------|----------------|-------|
| Вид товару / Користувач | `group_odomate_product_kind_user` | Перегляд дерева видів, бачить класифікацію на документах |
| Вид товару / Менеджер | `group_odomate_product_kind_manager` | Повний CRUD довідника **та** виключне право змінювати зафіксовані знімки |

Група Менеджер успадковує групу Користувач. Глобальне мультикомпанійне правило
запису дозволяє користувачу одночасно бачити **глобальні** (без компанії) види та
види **всіх дозволених йому компаній**.

- **Працює одразу після встановлення.** Встановлення модуля автоматично надає
  адміністратору групу *Вид товару / Менеджер*, тож меню **Види товару** та
  повний доступ доступні одразу — без ручного налаштування груп.
- **Кожен внутрішній користувач може читати довідник.** Окрім двох спеціальних
  груп вище, усі внутрішні користувачі (базова група *Внутрішній користувач*)
  отримують доступ на читання до `odomate.product.kind`. Саме це дозволяє
  будь-якому користувачу відкрити товар, рядок замовлення на продаж,
  специфікацію чи виробниче замовлення з видом товару, не отримавши помилку
  доступу — навіть якщо його не додано до групи Вид товару / Користувач. Лише
  створення, редагування чи видалення видів усе ще потребує спеціальних груп.

## 4. Довідник Видів товару

Відкрийте **Виробництво ▸ Налаштування ▸ Види товару**.

Типовий вигляд — **Ієрархія** (перетягуваний вигляд тек). Також можна перемкнутися на:

- **Список** — плаский, сортований, із повним шляхом у `complete_name`.
  Перетягуйте рядки за маркером послідовності, щоб змінити порядок — він
  відображається в цьому списку, в Канбані та в Ієрархії.
- **Канбан** — типово згрупований за батьком (ієрархія), з лічильником
  товарів на картці. Групування за типом маршруту чи режимом виробництва
  доступне вручну в будь-який момент.
- **Форма** — деталі класифікації плюс чотири смарт-кнопки. Вкладка
  **Підвиди** має власний маркер для перетягування дочірніх записів.

### Поля

| Поле | Значення |
|------|----------|
| `name` | Назва. Унікальна серед **дітей одного батька**, в межах однієї компанії/глобальної області видимості (див. §7) — та сама назва може повторюватися під іншим батьком. |
| `code` | Короткий бізнес-код. Унікальний у межах компанії, а також окремо серед глобальних видів (див. §7). |
| `sequence_code` | Короткий код (напр. `PRD`, `SF`, `CMP`), зарезервований під **автонумерацію** ECO, специфікацій і товарів — окремий від `code`, унікальний так само в межах компанії/глобально. |
| `color` | Колір із color-picker для візуального кодування виду в Канбані та Ієрархії. |
| `description` | Текстовий опис виду. |
| `complete_name` | Автообчислюваний шлях, напр. `Готова продукція / Меблі`. |
| `route_type` | Продається / Виробляється / Напівфабрикат / Комплектуюча / Послуга / Транспорт / Інше. |
| `manufacturing_mode` | Успадкувати / На замовлення / На склад / Вручну / Вимкнено. |
| `requires_engineering`, `requires_team_planning` | Прапорці планування. |
| `parent_id` / `child_ids` | Структура дерева (`_parent_store`). |
| `company_id` | Залиште порожнім для **глобального** виду, спільного для всіх компаній. |

### Смарт-кнопки

Кожна кнопка рахує записи по **всьому піддереву** (через `child_of`), тож
кореневий вид показує підсумки всіх своїх нащадків. Підрахунок включає
**архівовані** види, товари, специфікації, рядки продажу та виробничі
замовлення, тож цифри лишаються стабільними й не «стрибають» через
архівацію чогось у піддереві:

- **Товари** — шаблони товарів із цим видом.
- **Специфікації** — специфікації, чий товар несе цей вид.
- **Рядки продажу** — рядки замовлень, класифіковані тут (жива прив'язка).
- **Виробництво** — виробничі замовлення, чий **знімок** потрапляє в це піддерево.

## 5. Класифікація товарів

На будь-якому **шаблоні** товару (**Склад / Продажі ▸ Товари ▸ Товари**)
відкрийте вкладку **Вид товару**, щоб знайти поле **Вид товару**. Вибір виду
відкриває на тій самій вкладці чотири readonly-атрибути — Тип маршруту,
Режим виробництва, Потрібна інженерія, Потрібне планування бригад —
віддзеркалені з виду.

І список/пошук Товарів, і список/пошук Специфікацій пропонують фільтр
**Групувати за: Вид товару**, тож можна згрупувати товари чи специфікації за
класифікацією, не відкриваючи сам довідник Видів товару.

Поле також доступне з форми **Варіанта товару** в модулі **Продажі**
(**Продажі ▸ Товари ▸ Варіанти товару**), одразу після категорії товару. Вид
товару — це атрибут **рівня шаблону**: усі варіанти одного шаблону мають одне
спільне значення. Встановлення чи зміна виду з варіанта одразу оновлює
шаблон, і нове значення відображається на всіх інших варіантах та на формі
шаблону — окремого значення на кожен варіант не існує. Редагованість скрізь
однакова: будь-який користувач із правом запису на товар може встановити
вид, без потреби у спеціальній групі Вид товару.

Список **шаблонів товару** та список **варіантів товару** (Продажі ▸ Товари)
також пропонують Вид товару як опціональну колонку — увімкніть її через
вибір колонок (іконка ⊕), якщо вона не показана типово.

Прив'язка товар ↔ вид та прив'язка **специфікації** завжди **живі**: змініть вид
товару — і обидві оновляться миттєво.

## 6. Ланцюжок знімка (товар → продаж → виробництво)

Це серце модуля.

1. **На комерційній пропозиції (чернетка)** — рядок замовлення показує `Вид товару`
   як живе readonly-відображення поточного виду товару. Знімка ще немає.
2. **Гейт 1 — підтвердження замовлення** — `action_confirm()` копіює поточний вид
   у `Вид товару (знімок)` на кожному рядку, що ще не має знімка. Раз зафіксований,
   він **ніколи** не перераховується, навіть при поверненні в чернетку й повторному
   підтвердженні.
3. **Гейт 2 — створення виробничого замовлення** — знімок встановлюється один раз
   за пріоритетом: **знімок рядка продажу** → інакше **поточний вид товару**.
   Ручне MO без пов'язаного замовлення завжди бере вид товару на момент створення.

*Менеджер видів товару* може виправити вже зафіксований знімок безпосередньо з
форми рядка продажу або виробничого замовлення — поле знімка редаговане для
менеджерів і залишається readonly для всіх інших користувачів, на обох
документах.

І рядок продажу, і виробниче замовлення також пропонують readonly-колонку/поле
**Тип маршруту (знімок)** — швидке довідкове відображення типу маршруту
зафіксованого виду, без потреби відкривати запис Виду товару.

### Робочий приклад

- «Модульна полиця» класифікована як **Меблі**.
- Замовлення **S00042** підтверджено → знімок його рядка фіксується на **Меблі**.
- Створено виробниче замовлення → його знімок фіксується на **Меблі**.
- Пізніше хтось перекласифіковує «Модульну полицю» на **Напівфабрикат**.
- **Результат:** товар та його специфікація тепер показують **Напівфабрикат**
  (живе), тоді як рядок S00042 та виробниче замовлення досі показують **Меблі**
  (зафіксовано). Ваша виробнича історія залишається достовірною.

## 7. Звітність у Sales Analysis

Вид товару та Тип маршруту доступні як виміри **Групувати за** та фільтри
пошуку в **Продажі ▸ Звітність ▸ Продажі** (звіт Sales Analysis — зведена
таблиця / графік / список).

- Відкрийте звіт, натисніть стрілку випадного меню в рядку пошуку і знайдіть
  у розділі **Групувати за** пункти **Вид товару** та **Тип маршруту** — або
  введіть будь-яку з цих назв прямо в рядок пошуку, щоб відфільтрувати.
- Показане значення підпорядковується тому самому правилу **спочатку
  знімок, інакше живий вид**, що й скрізь у модулі: рядок із **підтвердженого**
  замовлення звітує за видом, **зафіксованим при підтвердженні** (як і сам
  рядок замовлення на продаж), тоді як рядок **чернетки/комерційної
  пропозиції** — що ще не має знімка — звітує за **поточним** видом товару.
- Рядок, чий товар взагалі не має Виду товару, групується як «Немає» за
  обома вимірами.

### Робочий приклад

Продовжуючи приклад із «Модульною полицею» з §6: після підтвердження S00042
і подальшої перекласифікації товару з **Меблі** на **Напівфабрикат**, звіт
Sales Analysis за цей період усе ще показує рядок S00042 під **Меблі** — він
звітує за зафіксованим знімком, а не за поточною класифікацією товару. Нова
комерційна пропозиція на той самий (уже перекласифікований) товар звітує під
**Напівфабрикат**, оскільки знімка в неї ще немає.

## 8. Бізнес-правила та гарантії

- **Незмінність знімка (модельний рівень).** Щойно знімок встановлено, змінити
  його може лише *Менеджер видів товару*. Будь-який інший користувач при спробі
  зміни — навіть через прямий API/імпорт, а не лише через форму — отримує
  `UserError`. Поле знімка у формі readonly для всіх, крім менеджерів, які
  можуть редагувати його прямо на формі рядка продажу чи виробничого
  замовлення (див. §6).
- **Архівація.** Вид не можна архівувати, доки він має **активні підвиди**
  (блокується для всіх). Додатково, не-менеджери не можуть архівувати вид, доки
  його використовують **активні товари**; менеджер може.
- **Видалення захищене.** Видалення Виду товару, що має підвиди, блокується з
  чіткою помилкою («Cannot delete Product Kind '...' because it still has N
  sub kind(s). Delete or reparent them first.»). Видалити можна лише **лист**
  (без нащадків) — видалення батька більше не каскадно стирає все піддерево.
- **Унікальність.** `code` і `sequence_code` кожен унікальний у межах компанії,
  а також окремо серед глобальних видів. `name` унікальна серед **дітей одного
  батька** (в межах однієї компанії/глобальної області) — не по всій компанії,
  тож та сама назва (напр. «Metal») може існувати під різними батьками, але не
  двічі під одним. Глобальні види скрізь мають власні partial unique indexes,
  бо SQL інакше трактує кожен `NULL` company/parent як різний. Створення чи
  перейменування виду в конфлікт викликає чітку перекладену помилку з
  зазначенням точного дубліката — ніколи не пряму помилку бази даних — ще до
  збереження запису; індекси бази даних лишаються під капотом як страховка на
  випадок конкурентних записів.
- **Без циклів.** Прив'язка до батька перевіряється на рекурсію.

## 9. Довідка по виглядах

| Модель | Де з'являється поле |
|--------|---------------------|
| `product.template` | Форма: вкладка «Вид товару» з полем + похідні атрибути. Список (Продажі ▸ Товари ▸ Товари): опціональна колонка. Пошук: фільтр «Групувати за: Вид товару». |
| `product.product` | Форма (Продажі ▸ Товари ▸ Варіанти товару): «Вид товару» поруч із категорією — те саме значення рівня шаблону, редаговане тими самими користувачами, що й на формі шаблону. Список: опціональна колонка. |
| `sale.order.line` | Опціональні (`optional="hide"`) колонки виду, знімка та «Тип маршруту (знімок)» — знімок редаговане лише для Менеджера видів товару |
| `mrp.production` | Знімок + readonly «Тип маршруту (знімок)» у зоні класифікації — знімок редаговане лише для Менеджера видів товару, readonly для всіх інших |
| `mrp.bom` | Readonly-колонка Виду товару (жива). Пошук: фільтр «Групувати за: Вид товару». |
| `sale.report` (Продажі ▸ Звітність ▸ Продажі) | Вид товару та Тип маршруту як пошукові поля та фільтри «Групувати за» (спочатку знімок, інакше живий вид — див. §7). Readonly, як і решта звіту. |

## 10. Обмеження

- Знімок виробничого замовлення успадковується від рядка продажу лише коли ваша
  інсталяція пов'язує MO з рядками продажу (поле `sale_line_id` на
  `mrp.production`). Без цього містка кожне MO бере поточний вид товару на момент
  створення; наявність прив'язки визначається захищено під час виконання.
- Поле `manufacturing_mode` фіксує намір (На замовлення / На склад / …) для
  звітності та подальшої автоматизації; сам модуль не змінює маршрути постачання
  Odoo.
- Лічильники смарт-кнопок обчислюються при читанні (не зберігаються) і відображають
  поточний стан бази даних при кожному відкритті форми.
- Фільтри «Групувати за: Вид товару / Тип маршруту» у Sales Analysis
  додаються до того пошукового вигляду, який Odoo зараз використовує для
  `sale.report` (визначається динамічно, оскільки технічний ID цього вигляду
  нестабільний між версіями Odoo). Цей патч **самовідновлюваний**: він
  перебудовується заново при кожному встановленні *та* при кожному
  наступному оновленні модуля, тож він автоматично усувається, якщо колись
  залишився застарілим чи «осиротілим» (наприклад, через перерване або
  застаріле видалення модуля) — вручну редагувати базу даних ніколи не
  потрібно. Якщо розділ Продажі ▸ Звітність видає помилку вигляду з
  посиланням на поле `odomate_*`, оновлення цього модуля (Додатки ▸ Product
  Kind — Manufacturing Classification ▸ Оновити) усуває проблему. Видалення
  модуля також коректно прибирає цей патч, тож він ніколи не залишає
  застарілого посилання для наступного встановлення.
